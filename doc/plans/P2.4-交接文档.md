## 3. P2.4 要做什么：最小 W1 Core（Scene DB 提前）

### 一句话
**无 UI 的 Authoring 数据核心**——让"游戏对象怎么定义/编辑/查询"有真正的 W1 数据层（不是编辑器 UI），成为**后续唯一的新 Authoring 数据入口**，不等 P6 才接触目标产品。

### 背景（为什么提前）
架构宪法把 W1 Authoring 当核心，但之前 P2/P3 一直用**临时 Authoring**（`ShooterGame.Install` 里手写 `InsertState`/`SpawnNow`）。你定的"一步到位（宪法 7）"决定**提前**——否则架构没有真正的 W1 数据入口。

### 要实现的产物（从总方案 P2.4 行）

| 产物 | 说明 | 现状/参考 |
|---|---|---|
| **Stable Object ID** | 对象稳定身份（编辑期/运行时都可用，非 NodePath） | 现在 `Entity` 有 Id+Revision |
| **Component Schema** | 组件元数据（`[Component]` 声明→生成器统一注册/序列化/Inspector） | 现有 `IComponent` + 生成器 |
| **Relation** | 对象间关系（一等公民，非父子树） | Friflo 有 `IRelation`/`ILinkComponent` |
| **Query** | 结构化查询（"所有 Health<50"——人/AI 共用） | 现有 `ForEach/Read` |
| **Transaction/Undo** | 事务化修改（UI 和 MCP 产生相同事务，可撤销） | **全新**（P2.4 核心新增） |
| **确定性持久化** | 稳定可序列化存储（Git 友好） | MemoryPack（后续） |
| **最小 Baker** | W1 数据 → W2 ECS 编译 | **全新**（P3 脊柱，先做最小版） |

### P2.4 退出条件（门禁，来自总方案）
- 同一操作经 **UI 和 MCP 产生相同事务与 diff**
- **Undo/Redo 后 Artifact hash 完全恢复**
- **Rename/Reparent 不破坏引用**
- 单组件修改只重烘相关对象
- Prefab override 可查询可解释
- 删除所有表现 Node 后模拟测试仍通过

## 4. 关键概念（你必须先建立的心智模型）

### 4.1 Object+Components ≈ ECS（宪法 + 定案）
> **Object ≈ Entity**（Object = 人类能理解的 Entity）；Component 是数据；行为 = System。`PlayerBundle`/`EnemyBundle` 是"组件配方"，不是类。

### 4.2 五世界分域权威（W1-W5）
- **W1** Authoring World（Object/Component/Relation——编辑期内容权威）
- **W2** Simulation World（C# ECS——Gameplay 权威）
- **W3** Physics / **W4** Render / **W5** Services
- W1 → Baker → W2；W2 是 Gameplay 权威，W3/W4/W5 是投影/服务

### 4.3 组件四分类（划分规则）
| 类别 | 判断句 | 示例 |
|---|---|---|
| 能力特征 | 它**能不能/会不会**做这事？ | `PlayerInput`/`SeekTarget` |
| 运行状态 | 它**现在**是什么值？ | `Position`/`Cooldown` |
| 每实体参数 | 这个实例的**规则数值**？ | `MoveSpeed`/`WeaponConfig` |
| 标签关系 | 它**属于谁/扮演什么关系**？ | `PlayerFaction`/`EnemyFaction` |

### 4.4 WorldState vs Component
- `world.State`（`WorldState`，借前端 store）+ `InsertState/GetState`（像 store.setState/getState）
- `XxxState` = 单个状态内容（如 `MatchState`）

### 4.5 分层定位
- **Baize.Ecs 日常入口**（EcsSystem/ForEach/ForTag/InsertState）+ **Friflo 底层内核**（IComponent/Entity/ref——性能核心，有意保留）
- 深度用户可直接 Friflo（不封死）

## 6. P2.4 建议的实施顺序

1. **Schema 先行**：定义 `[Component]`/`[Relation]` 元数据 + 生成器统一注册（扩展现有 AOT/Feature 生成器）
2. **Stable ID + 对象模型**：W1 Object（非 Entity）——稳定身份，与 W2 Entity 映射
3. **Transaction/Undo**：核心新增——记录修改（Add/Remove/Set 组件）为事务，可 Undo/Redo
4. **Query**：结构化查询（人/AI 共用——"Health<50 的敌人"）
5. **最小 Baker**：W1 数据 → W2 ECS 编译（产出 `IRuntimeSceneSource`，不改 W2 契约）
6. **确定性持久化**：可序列化（MemoryPack），Git 友好

**关键**：先做最小可用（Schema + Stable ID + Transaction），再 Baker——**别一开始做完整编辑器 UI**（UI 是 P6B）。

## 7. 已知坑（同事请注意）

1. **确定性**：Gameplay 任何随机用 `TickIndex` + 确定性 hash（SplitMix64 风格），**不用 `System.Random`**（破坏回放）
2. **结构变更**：查询循环内**禁止**直接 `CreateEntity`/`AddComponent`（Friflo 抛异常）——统一走 `WorldCommandBuffer`
3. **生成器 additive-only**：不能改已有 `Install`——Feature 加 `partial` + 删手写 `Install`
4. **BOM**：新 `.csproj` 需 UTF-8 BOM（file-format 检查）；文件头 SPDX
5. **引用 F5**：Godot 项目引用普通 .NET 类库（Baize.Ecs）+ Godot.NET.Sdk——若 F5 报 SDK 解析，重启编辑器（GodotTools 已修复）
6. **共享库**：Gameplay 逻辑放 `shooter-gameplay`（零 Godot），console/godot 复用——**不做源码复制**
